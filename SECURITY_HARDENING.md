# Security hardening deployment notes

This branch introduces security controls that require coordinated environment configuration before deployment.

## Required server environment variables

- `JWT_SECRET`: a newly generated random secret of at least 32 bytes. Rotate the previous value; do not reuse any value that appeared in source control.
- `PORTAL_ADMIN_EMAIL`: the administrator login email.
- `PORTAL_ADMIN_PASSWORD`: a newly generated administrator password. Do not reuse the previously embedded password.
- `INTERNAL_API_SECRET`: a newly generated random secret of at least 32 bytes, shared only by the backend and trusted Cloudflare Worker.
- `GOOGLE_CLIENT_ID`: the exact OAuth client ID used by the Google sign-in client.
- `CORS_ORIGINS`: comma-separated exact browser origins, for example `https://example.com,https://www.example.com`.

## Required Cloudflare Worker secrets / vars

Set `JWT_SECRET` to the same JWT verification secret used by the backend and set `INTERNAL_API_SECRET` to the same internal-service secret. Configure these as Worker secrets, not source-controlled vars.

## Compatibility notes

- The client-writable `/api/auth/stats` and `/api/auth/sync-wallet` endpoints now return HTTP 410. Progress and wallet mutations must be generated by trusted server-side match/reward processing.
- Admin question routes require a short-lived portal admin JWT.
- Log inspection, streaming, clearing, and simulation endpoints require portal admin authorization.
- Telegram admin endpoints require portal admin authorization.
- Avatar upload requires a verified, non-guest bearer token and accepts JPEG, PNG, or WebP payloads up to the configured request cap.
- Room provisioning and internal match-result/question endpoints fail closed when the internal secret is missing or invalid.

## Operational actions

1. Rotate any credentials or tokens that were committed previously, including the admin password, JWT secret, Telegram bot token if exposed, and any other keys found in Git history.
2. Update server and Worker secrets before deploying this branch. Missing secrets intentionally cause relevant operations to fail closed.
3. Verify all allowed frontend origins are listed in `CORS_ORIGINS`.
4. Run the server and Worker build/test suites, then perform authenticated integration tests for login, profile, purchases, matchmaking, room creation, and final match settlement.
5. Review Supabase RLS policies and database service-role key handling separately; this code change cannot verify dashboard-side policies.
